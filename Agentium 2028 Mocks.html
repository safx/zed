判断はどこに保存するか

  • 正は 3 か所で、どれも Agentium 無しで読める。 commit trailer (ポインタだけ)、PR 説明文の ## Decisions (エージェントの判断)、Backlog 課題コメント (人の判断と、課題を閉じるときの一覧)。
  • Agentium のローカル (data_dir) に置くのは 3 つだけ。 ID の採番、Backlog に投稿する前の outbox、bee / gh の ETag キャッシュ。すべて上の 3 か所から再構築できる。
  • ID の採番だけは中央が要る。 2 リポジトリと並列エージェントが同時に D-747-2 を取り得るので、agentium decision new --issue 747 (方向 5 の CLI) で採番するか、ID に短い suffix を付ける。
  • hunk 単位の台帳は任意の拡張。 proof (どのコマンドで検証したか) を足したくなったときだけ、hook の実データを使う。Edit の PostToolUse には hunk ヘッダそのもの (structuredPatch) と prompt_id / tool_use_id が入り、失敗コマンドは PostToolUseFailure の error: "Exit code 3\n…" で exit code が取れる (実測)。transcript は cleanupPeriodDays (既定 30 日) で消えるので参照しない。

落とし穴

  • squash merge。 GitHub は既定で全 commit メッセージを連結するので trailer は残る。Backlog の squash 挙動は未確認。消えても blame → squash commit → PR 説明文のフォールバックで引ける。
  • フォーマッタの commit が blame を奪う。 git blame -w -M -C と --ignore-revs-file で逃がす。
  • 判断ごとに commit を分ける運用が崩れると、1 commit に判断が 2 つ以上乗る。 trailer は複数行書けるので Decision: を複数付ける形を許す。
  • Codex は hooks が既定で有効になった (公式 docs)。 ただし非 managed の command hook は /hooks で信頼する手順が要り、repo 配下の hooks.json だけ置いた codex exec は 180 秒経っても動かなかった。payload の中身は未検証。

タスクを作業の入口にする

左ペインはタスク・Arenaの所属と集約状態を示します。エージェントの行やTodo本文は置かず、従来の実行中・完了・許可待ち・失敗・プロセスのバッジに、未処理Todoの合計を追加します。

確認できる操作

  • タブバーの＋からTask Overviewを開く。閉じた後も同じ入口から再表示できます。
  • Todo合計をクリックすると、対象タスクのOverviewを開きます。独立したTodoタブはありません。
  • OverviewではArenaごとに各エージェントの依頼・結果・Todoを表示します。返信先と内容を確認して送信すると、該当エージェントの残件と左ペインの合計が減ります。
  • 変更・会話・返信履歴、PRの確認と、元のエージェントタブへの移動を試せます。操作はすべてモック内だけで反映されます。
  • タスクやタブを切り替えても返信の下書きを保持します。コーディネーター欄は将来案で、送信できません。
